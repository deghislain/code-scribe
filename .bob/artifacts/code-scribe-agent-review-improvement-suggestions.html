What's Working Well

Checkpoint-based resume

The 13-step orchestrator uses CP_* constants and an idempotent set_checkpoint upsert so any job can resume from its last successful step after a crash. The two-phase PDF rendering (probe then stamp version) ensures no orphan DB record is written if WeasyPrint fails. This is solid defensive design.

Layered stack detection

detector.py correctly sequences heuristics: dependency files → import scanning → LLM fallback. The second-pass scan of root-level .py imports when no framework keyword appears in lock files is a nice real-world workaround for truncated uv.lock blocks.

Self-contained injected widget

The Streamlit widget (chat_widget_st.py) calls Groq directly and carries its own .env loader — no Code-Scribe backend process is needed at runtime. The idempotent guard comment (# code-scribe: chat_widget) prevents double-injection cleanly.

Good memory abstractions

store.py keeps all SQLite access behind thin functions, uses ON CONFLICT ... DO UPDATE for safe upserts, and handles additive migrations by swallowing duplicate column errors — a pragmatic schema evolution strategy.

Architecture Observations

Architecture Single-threaded orchestrator on a shared DB

All 13 steps run sequentially in a single background thread, and the global _current_job_id / _app_proc state means only one job can ever run at a time. This is fine for a personal tool but will become a problem as soon as multiple users or repositories are queued simultaneously. The shared mutable globals bypass the lock in cancel_running_jobs because _stop_event is cleared inside _register_job without re-acquiring the same lock object — a subtle race on restart.

Suggestion: Replace global mutable state with a per-job context object (a small dataclass) passed through the pipeline. Queue jobs with asyncio.Queue or a simple in-process task queue.

Architecture builder.py duplicates start-command logic

start_app() and verify_chat_widget() contain near-identical if/elif trees for building the launch command (~60 lines each). A future third caller (e.g. a restart-after-hot-reload feature) would require a third copy.

Suggestion: Extract a _build_launch_cmd(repo_dir, stack_profile) -> list[str] | None helper that both functions share.

Architecture sync_monitor._regenerate re-detects the stack every cycle

On every poll cycle that finds new commits, _regenerate calls detector.detect(repo_dir) again — potentially making several LLM calls if the LLM fallback path is triggered. The stack rarely changes between commits.

Suggestion: Read the cached stack_detected checkpoint evidence (which already contains the full StackProfile JSON) instead of re-running detection.

Design Hard-coded LLM provider

Groq is the only LLM backend. The llm.py module imports groq directly; there is no interface that a different provider could implement. Swapping to an OpenAI-compatible endpoint or a local Ollama instance requires modifying llm.py itself.

Suggestion: Introduce a thin provider protocol (two methods: ask, ask_structured) and move Groq behind a GroqProvider implementation. The config gains a LLM_PROVIDER key. This is one file change with zero impact on callers.

Design doc_generator._tree_listing is duplicated

Identical functions _tree_listing and _read_safe appear in both detector.py and doc_generator.py. Any bug fix must be applied twice.

Suggestion: Move these two utilities to a shared backend/agent/utils.py module and import from there.

Design & Code Quality Improvements

Perf SQLite connections opened per call

Every store.* function calls get_db_connection(), which opens a new sqlite3.connect(). During a 13-step pipeline with dozens of checkpoint writes this creates many open/close cycles. For a single-writer SQLite workload, a connection pool (threading.local with one connection per thread) would reduce I/O overhead and eliminate the repeated PRAGMA negotiation.

Security Credentials written to the target repo's .env

_inject_streamlit writes GROQ_API_KEY and GROQ_MODEL directly into the analysed repository's .env file. If the repo is later pushed to GitHub (e.g. the developer runs git push in their cloned workspace), the API key leaks publicly. The .gitignore of the target repo may not list .env.

Suggestion: Check .gitignore in the target repo before writing credentials; if .env is not ignored, emit a warning in the log and write a separate .env.scribe file (which is added to .gitignore automatically).

Design _run timeout is fixed at 300 s for all languages

A 300-second timeout is too short for Java Maven full builds but unnecessary for Go or Rust incremental builds. A large Maven project fetching artifacts cold will be killed with a cryptic "Command timed out after 300 seconds" error that maps to blocked status.

Suggestion: Make the timeout a parameter to _run and pass language-specific values from install_deps / build (e.g. 600 s for Java, 120 s for Go/Rust).

Design Acceptance criteria 14_documents_saved is too weak

The criterion passes if any document exists for the job, even if only one of two guides was generated. The plan requires both user_guide and dev_guide.

Suggestion: Change the check to verify both "user_guide" and "dev_guide" are present in doc_types.

UX No progress percentage surfaced to the frontend

The orchestrator logs step numbers ([1/12], [8/12]) but the WebSocket and REST API only return raw checkpoint status. The frontend has no way to show a meaningful progress bar without re-counting checkpoints client-side.

Suggestion: Add a progress_pct field to the job record (or compute it in the GET /api/jobs/current response) as done_checkpoints / total_checkpoints * 100.

Design generate_user_guide hardcodes sections: 13

Both guide generators call store.set_checkpoint(..., "done", {"sections": 13}) with a literal integer rather than the actual count of tasks generated. If a section is added or removed, the evidence becomes misleading.

Suggestion: Pass len(tasks) instead of a hard-coded number.
